# 会话状态性能基准

```bash
pnpm bench:runtime
pnpm bench:runtime --outputJson /tmp/maxcode-runtime-before.json
# 修改后，在同一台机器、相同 Node 版本和负载下比较：
pnpm bench:runtime --compare /tmp/maxcode-runtime-before.json --outputJson /tmp/maxcode-runtime-after.json
```

基准位于 `benchmarks/conversation-runtime.bench.ts`，使用独立的
`vitest.bench.config.ts` 和 Node 环境，约需 12 秒。普通 `pnpm test` 和 CI
单元测试不运行这些基准。没有耗时阈值断言；比较前关闭构建、测试和其他高负载任务，
出现回退时重复运行并关注均值、p99、误差范围，而非一次测量中的最快值。

## 测量内容

流式场景调用真实的 `setLiveMessage` reducer 和 `selectTimelineTurns`，包含状态更新、
文本/工具内容归一化、时间线拼接与缓存读取。仅隔离网络 API，意外读取网络会报错。
固定数据和时间戳确保每次工作量相同；每批创建新的实时消息对象，正在输出的工具也会
创建新的 chunks 数组，避免重复播放同一对象导致缓存失真。

| 场景 | 固定工作量 | 一次 operation 的含义 |
| --- | --- | --- |
| 首次构建历史 | 2,000 / 10,000 条 user、assistant 交替的历史 | 注入状态并首次构建时间线，使用新 detail 对象绕过缓存 |
| 长历史 + 文本 | 120 / 2,000 / 10,000 条历史，92 KiB 实时回复 | 连续 32 批文本追加，每批更新状态并读取时间线 |
| 大量工具输出 | 2,000 条历史，40 个已完成工具各 8 KiB，一个运行中工具已有 256 KiB | 连续 32 批，每批增加 1 KiB 并读取时间线 |
| 保留多个会话 | 8 个会话各 2,000 条历史，1 / 8 个正在输出 | 32 轮更新；每次状态更新后读取全部 8 个会话的选择器，共 32 / 256 批 |

120 条对应默认历史尾部窗口，2,000 和 10,000 条模拟向上翻页后加载的长历史。
历史数据生成、初始种子状态和流式场景的首次缓存预热不计时；首次构建场景计入状态注入，
但不计网络、JSON 解析。每个场景预热 250 ms，正式采样至少 1,000 ms、20 次。
测量外还校验最终文本、工具输出长度和运行状态，以及空闲会话时间线引用没有变化。

## 初始记录（2026-09-26）

代码基线 `d70656d3`，macOS arm64 / Apple M4 / Node v24.19.0 / Vitest 2.1.9。
以下是本地单次采样；采样期间有其他验证任务运行，仅作初始量级参考。
评估改动收益时应在空闲环境重跑基线，不把本表作为跨机器通过标准。

| 场景 | 均值（ms / operation） | p99（ms / operation） |
| --- | ---: | ---: |
| 首次构建 2,000 条 | 0.5069 | 4.8902 |
| 首次构建 10,000 条 | 3.4015 | 12.8486 |
| 120 条 + 文本，32 批 | 0.0723 | 0.2367 |
| 2,000 条 + 文本，32 批 | 0.1927 | 4.1710 |
| 10,000 条 + 文本，32 批 | 0.4756 | 7.3670 |
| 工具输出，32 批 | 3.9258 | 18.3029 |
| 1 个会话输出 / 8 个保留，32 批 | 0.1751 | 3.7931 |
| 8 个会话输出 / 8 个保留，256 批 | 1.8519 | 9.9314 |

这些数据仅衡量状态计算。基准没有挂载 React、解析 Markdown、语法高亮、布局、滚动、
输入交互或 WebSocket 定时批处理，也不测内存峰值或泄漏，不能据此承诺会话打开耗时、
输入延迟或 UI 帧率。排查实际卡顿时，需要在 Electron/浏览器中使用同量级历史、工具
输出及分屏会话录制 Performance，并核对 React 提交耗时、长任务和输入响应；检查
内存时还应反复打开、关闭会话并对比 GC 后的 heap snapshot。
